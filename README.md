# Пиццаед — API-автотесты на Python

Набор API-автотестов интернет-магазина доставки пиццы на **Python, pytest и requests**. Проверяет каталог, корзину, оформление заказов, расчёт скидок и доставки, валидацию запросов и изоляцию данных между сессиями.

## Что реализовано

- Позитивные и негативные сценарии, граничные значения и параметризованные проверки.
- Независимые сессии через фикстуры pytest и генерация данных покупателя для каждого вызова.
- Проверка сохранённого состояния через GET после добавления, изменения, удаления и отказа оформления.
- Воспроизведение известного API-дефекта через строгий `xfail`, который не скрывает посторонние ошибки.
- Единое форматирование и статическая проверка Ruff, чек-лист и баг-репорты со скриншотами.
- Конфигурация GitHub Actions для автоматического запуска и формирования Allure-отчёта.

## Стек

- Python — генерация данных и реализация тестов; проверено на версии 3.14.2.
- pytest — запуск, фикстуры, параметризация и отметки известных дефектов.
- requests — HTTP-запросы к API.
- allure-pytest и Allure Report 3 — сбор результатов и HTML-отчёт.
- GitHub Actions — конфигурация CI.
- Postman — ручное исследование запросов и ответов.

Версии зависимостей закреплены в [requirements.txt](requirements.txt).

## Покрытие

| Область | Основные проверки |
| --- | --- |
| Каталог | Получение списка и товара по ID, `404` для отсутствующего товара, фильтрация по категории и наличию, поиск по названию, описанию и бейджам |
| Корзина | Новая пустая корзина, добавление и повторное добавление, изменение количества, удаление через DELETE и PATCH с количеством 0, запрет недоступного товара |
| Количество | Приём 20 единиц, сохранение лимита при повторном добавлении, отклонение отрицательного, дробного количества и 21 через POST и PATCH |
| Доставка | Платная и бесплатная доставка, сумма ровно 1500 ₽, возврат платной доставки после уменьшения количества |
| Промокод | QA60, регистр, пробелы по краям, неверный и пустой код, бесплатная доставка при снижении суммы после скидки ниже 1500 ₽ |
| Заказы | Успешное создание, статус и контактные данные, расчёт суммы, очистка корзины, отказ при пустой корзине |
| Валидация заказа | Отсутствие, пустые строки и пробелы в обязательных полях; сохранение корзины и истории после отказа; неверные типы полей с отметкой BUG-004 |
| Сессии | Независимость корзин и истории заказов двух сессий |


## Установка

Нужны установленный Python и доступ к `https://aiqa.su`. Команды ниже выполняются в PowerShell из корня проекта.

```powershell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Если окружение уже создано, достаточно установить зависимости. Активировать его необязательно: команды явно используют Python из `.venv`.

## Запуск

Весь набор с кратким описанием ожидаемых падений:

```powershell
.\.venv\Scripts\python.exe -m pytest -v -ra
```

Отдельный файл:

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_cart.py -v
```

Один тест:

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_orders.py::test_discount_does_not_cancel_free_delivery -v
```

Посмотреть список проверок без запросов к API:

```powershell
.\.venv\Scripts\python.exe -m pytest --collect-only -q
```

## Отчёт Allure

Плагин `allure-pytest` устанавливается из `requirements.txt`. Для генерации HTML используется Allure Report 3.22.1 через Node.js и npm; глобальная установка Allure не требуется.

Запуск со сбором Allure и JUnit XML:

```powershell
.\.venv\Scripts\python.exe -m pytest -v --alluredir=allure-results --clean-alluredir --junitxml=reports/junit.xml
```

Создание отчёта одним HTML-файлом:

```powershell
npx.cmd --yes allure@3.22.1 awesome allure-results --output allure-report --single-file --report-name "Pizzaed API Tests"
```

Открой `allure-report/index.html` в браузере. В PowerShell используется `npx.cmd`, чтобы не зависеть от политики запуска PowerShell-скриптов. Node.js нужен только для генерации HTML; обычные pytest-тесты запускаются без него.

`--clean-alluredir` очищает старые результаты Allure перед новым прогоном, чтобы не смешивать разные запуски. Результаты и отчёты исключены из Git через `.gitignore`.

В Allure ожидаемые падения pytest отображаются как пропущенные проверки с причиной `XFAIL`. Шесть случаев BUG-004 не означают успешную проверку валидации.

## CI — GitHub Actions

Конфигурация: [api-tests.yml](.github/workflows/api-tests.yml). Запуск предусмотрен при push, pull request и вручную через `Actions → API tests → Run workflow`.

Workflow устанавливает Python 3.14.2 и Node.js 24, затем:

1. Устанавливает зависимости из `requirements.txt`.
2. Проверяет Ruff и форматирование.
3. Запускает весь набор с Allure и JUnit XML.
4. Генерирует HTML-отчёт, даже если часть тестов упала и результаты успели сохраниться.
5. Сохраняет артефакт `api-test-results` на 14 дней: исходные Allure-результаты, HTML и `reports/junit.xml`.

Обычные падения тестов сохраняют красный статус CI. Генерация отчёта не превращает неуспешный прогон в успешный. Доступ к GitHub Pages и отдельные секреты для этого workflow не требуются.

Открой завершённый запуск в `Actions`, скачай `api-test-results` из раздела `Artifacts`, распакуй архив и открой `allure-report/index.html`. Это скачиваемый отчёт, без публикации сайта.

[Первый запуск в GitHub Actions](https://github.com/riqkyvf/pizzaed-api-tests/actions/runs/40713066343) завершился успешно: `54 passed, 6 xfailed`. Проверки Ruff и генерация Allure-отчёта также прошли.

## Организация тестов

Базовый адрес API находится в [config.py](config.py). Генератор покупателя в [data.py](data.py) возвращает новый словарь при каждом вызове: имя и адрес содержат UUID, телефон — числовой суффикс. Формат телефона генерируется для тестирования.

Фикстуры в `tests/conftest.py` создают уникальные значения заголовка `X-Course-Session` для каждого теста. Для проверок изоляции создаются две сессии. Тесты не используют пользовательскую корзину браузера и не зависят от порядка запуска.

Состояние корзины после операций подтверждается отдельными GET-запросами в соответствующих сценариях. HTTP-запросы используют тайм-аут 10 секунд и отключённые автоматические перенаправления.

## Стиль и проверка кода

Настройки pytest и Ruff находятся в [pyproject.toml](pyproject.toml). Ruff поддерживает единое форматирование, порядок импортов и проверяет типичные ошибки Python. Приняты отступы в 4 пробела и длина строки до 88 символов.

Ruff устанавливается вместе с остальными зависимостями из `requirements.txt`.

Проверки без изменения файлов:

```powershell
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe -m ruff format . --check
```

Применить форматирование:

```powershell
.\.venv\Scripts\python.exe -m ruff format .
```

## Известные дефекты

| Репорт | Проблема | Основание |
| --- | --- | --- |
| [BUG-001](docs/bugs/BUG-001-promo-reset.md) | Интерфейс показывает неверные скидку и итог после изменения количества; при оформлении скидка учитывается | Нарушение требования; проверялось вручную |
| [BUG-002](docs/bugs/BUG-002-fail-info.md) | В сообщениях об обязательных полях используются технические названия | Потенциальный дефект понятности сообщений |
| [BUG-003](docs/bugs/BUG-003-phone-validation.md) | Заказ оформляется с буквами или одним непробельным символом в телефоне | Потенциальный дефект; формат телефона не определён |
| [BUG-004](docs/bugs/BUG-004-order-field-types.md) | Число или boolean в контактных полях вызывает `500` вместо ошибки валидации | Известный дефект, воспроизводится в автотестах |

Проверки BUG-004 отмечены `xfail(strict=True)`. Ожидаемым падением считается только известный ответ `500` с сообщением о вызове `.trim` у соответствующего поля. Ошибки соединения и другие неожиданные ответы не маскируются.

После исправления BUG-004 корректный ответ `422` приведёт к `XPASS(strict)` и неуспешному завершению запуска: нужно проверить исправление и удалить отметку ожидаемого падения.

## Ограничения и основания проверок

- Тестируемый сервис «Пиццаед» размещён на учебной платформе AIQA и работает без реальной оплаты и доставки. Запросы создают и изменяют данные сервиса в отдельных тестовых сессиях.
- Проверки основаны на опубликованных требованиях и ручном исследовании. Возможности уточнить требования у автора проекта нет; предположения отделены от подтверждённых нарушений в баг-репортах.
- Тесты работают с общим каталогом. Проверки расчётов используют известные товары и цены; при их изменении тестовые данные нужно пересмотреть.
- Тест поиска вычисляет ожидаемые результаты из полного каталога. Он предполагает отсутствие пагинации и изменений каталога между двумя запросами.
- Округление скидки вниз не проверяется на дробном результате: текущие цены кратны 10 и дают целую скидку 10%.
